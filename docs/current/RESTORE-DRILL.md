## What already exists, and whether it was honest

[`docs/DISASTER-RECOVERY.md`](../DISASTER-RECOVERY.md) is the incident
runbook: four levels of damage, and the procedure for each. Read it for
*what to do when something breaks*. This file is narrower — it is the
**rehearsal**, and it exists because that document closes by admitting it
has never been rehearsed against Neon.

Its self-assessment was accurate on the point that matters: it says
plainly that the drill has never been run against a real Neon branch, and
that no RTO or RPO is committed because the numbers would be guesses.
That is the correct posture and this file inherits it.

⚠️ **Two things in it are now stale, and staleness in a DR document is a
defect.** It instructs you to pause the **Vercel** deployment and it
worries about **Vercel Blob**. Deployment is **Railway**, and object
storage is **Cloudflare R2** (`server/vault/`, `lib/storage/s3.ts`, the
`S3_*` variables). The procedure is right; the two names are wrong, and
at 3am a wrong name costs the minutes you have least of. `CONFIGURED`

### Why this file does not propose a `pg_dump` regime instead

Neon has point-in-time restore and branching, and the existing runbook is
built on them. That is the right primary mechanism: it is faster than any
dump-and-load, it needs no scheduled job that can silently stop, and it
restores to a *moment* rather than to the last time a cron happened to
succeed.

An off-provider dump is therefore **additive, and it answers exactly one
question the branch cannot**: what happens when the Neon account itself
is gone — suspended, disputed, or deleted by someone holding your
credentials. Neon's PITR lives inside the account it is protecting.
`ASSUMED · UNTESTED` — no off-provider dump is scheduled today, so this
paragraph describes a gap, not a mechanism. See
[Immutability, encryption, and the ransomware property](#immutability-encryption-and-the-ransomware-property).

## The drill

Set aside two hours the first time. Do it on a weekday morning when Neon
support is awake, not at midnight.

### Step 0 — Write down the start time

Actual clock time, on paper or in a note. Not "about ten". The whole
point of the exercise is this number.

> **Expected output:** a timestamp you wrote yourself, e.g. `10:04 IST`.

### Step 1 — Find out what your Neon retention actually is

Neon console → your project → **Settings** → **Storage / History
retention**.

> **Expected output:** a number of hours or days. Write it here the first
> time you look: **retention = `____`**.

🔴 **Do not skip this and do not assume the default.** If retention is
shorter than the time it takes you to *notice* a problem, PITR protects
nothing — you will discover the damage after the only moment worth
restoring to has expired. `ASSUMED · UNTESTED` — nobody has confirmed the
current value of this setting.

### Step 2 — Create the recovery branch

Neon console → **Branches** → **New branch** → *from a point in time* →
pick a timestamp ~1 hour ago. Name it `drill-YYYY-MM-DD`.

> **Expected output:** a branch listed with a **Created** timestamp and
> its own connection string.

🔴 **A branch, never a restore in place.** A branch leaves production
untouched, so a wrong choice of moment costs you a retry rather than the
evidence. This is the same instruction as Level 3 of the incident
runbook, and it is the most important sentence in either file.

### Step 3 — Note the branch-creation time

The console shows how long the branch took to become available.

> **Expected output:** seconds, typically. Write it down; it is the
> *cheapest* part of the RTO and the part people wrongly quote as the
> whole of it.

### Step 4 — Run the coherence harness against the branch

```bash
RESTORE_DATABASE_URL="postgresql://…the DRILL branch…" \
PRODUCTION_DATABASE_URL="$DATABASE_URL" \
  node scripts/verify-restore.mjs --i-know-this-is-a-restore
```

> **Expected output:** a `RESTORE COHERENCE` banner, a handful of `·`
> lines (table count, tenant-scoped tables all ENABLE + FORCE, audit
> chain rows), then `✅ The restored branch is COHERENT.` and exit code
> `0`.

What it refuses to do, and why, is in
[`scripts/verify-restore.mjs`](../../scripts/verify-restore.mjs): no
flag, no run; same host as `PRODUCTION_DATABASE_URL`, no run. **Zero
tables is a hard failure, not a clean pass** — a verifier that reports "0
problems found" against an empty database has certified nothing twice.

⚠️ If it reports tables that lost RLS, re-apply
`SQL-FILES/ALL-IN-ONE-SETUP.sql` to the branch and run it again **before**
pointing anything at the branch. A database with no row-level security
renders every page perfectly. The only difference is that every customer
can read every other customer's data.

### Step 5 — Verify the audit chain the slow way as well

```bash
# Paste SQL-FILES/VERIFY-0081-neon-safe.sql into the Neon SQL editor,
# with the DRILL branch selected in the branch dropdown.
```

> **Expected output:** section 1 shows `chain_columns = 4` and both
> booleans true; section 3 shows `broken_links = 0` per scope; section 4
> returns **zero rows** — zero rows there is the pass.

The harness runs the structural half of this automatically. Doing it once
by hand teaches you what the output looks like when it is healthy, which
is what you will be comparing against on the bad day.

### Step 6 — Count what a customer would notice

Pick your largest real tenant. In the Neon SQL editor, on the **drill
branch**:

```sql
SELECT (SELECT count(*) FROM contacts  WHERE tenant_id = 'THE-TENANT-UUID') AS contacts,
       (SELECT count(*) FROM companies WHERE tenant_id = 'THE-TENANT-UUID') AS companies,
       (SELECT count(*) FROM audit_logs WHERE tenant_id = 'THE-TENANT-UUID') AS audit_rows,
       (SELECT max(created_at) FROM audit_logs WHERE tenant_id = 'THE-TENANT-UUID') AS newest_audit_row;
```

> **Expected output:** counts within a rounding error of production, and
> a `newest_audit_row` at or just before your chosen restore point.

🔴 **`newest_audit_row` is the RPO measurement.** The gap between it and
the incident time is exactly how much work you lost. Write it in the
results table. Everything else in this step is reassurance; this line is
evidence.

### Step 7 — Point a throwaway app instance at the branch

Railway → a **new service or a preview environment**, never the
production service → set `DATABASE_URL` to the branch → deploy → sign in
→ open one customer record.

> **Expected output:** you are looking at the restored data in a browser.

⚠️ **This is the step that discovers the things a SQL query cannot.**
Sessions, the vault, R2 links. Expect some of it to be broken; see the
next section, which lists what will break and why.

### Step 8 — Stop the clock, then delete the branch

Write down the finish time. Compute the difference. Fill the table in.
Then delete the drill branch — a stale branch costs storage and, worse,
is one dropdown away from being connected to by mistake.

## 🔴 What a restore drill forgets — the four things not in your database

Restoring the database restores the database. Each of these will be
missing, and none of them will announce itself.

**1. The Clerk user directory.** Users, passwords, MFA enrolments,
organisation memberships and sessions live in **Clerk**, not in Postgres.
Restore the database to last Tuesday and your `users` rows point at Clerk
identities that may no longer exist or may have changed. If **Clerk** is
the thing that failed, no database restore signs anybody in.
`ASSUMED · UNTESTED` — no export or restore of the Clerk directory has
ever been performed here.

**2. R2 objects.** `documents` rows are metadata: a key, a size, a
content type. The **file** is in Cloudflare R2 (`lib/storage/s3.ts`,
`S3_BUCKET`). A perfect database restore gives you a document list where
every download 404s. R2 has its own lifecycle, and a database restore
does not roll it back — nor should it. `CONFIGURED` for storage;
`ASSUMED · UNTESTED` for any restore of it.

**3. Railway secrets.** Environment variables are in Railway. They are
not in any database dump and not in any Neon branch. A restore into a
fresh environment without them produces an application that boots into an
error page.

**4. 🔴 The vault key. `VAULT_ENCRYPTION_KEY` and
`VAULT_BLIND_INDEX_PEPPER` (`lib/env.ts`).** These are the ones that end
a company. Encrypted columns restore as ciphertext, and ciphertext
without its key is not data — it is noise with a schema.

> **A restored database with no vault key is a database of ciphertext.**

⚠️ **Therefore: the key must be stored somewhere that is not Railway and
not Neon**, because the scenario you are restoring from is often "the
account is gone". Written down on paper in a safe, or in a password
manager you personally control, counts. A copy in the environment you are
trying to recover does not. `ASSUMED · UNTESTED` — whether an off-platform
copy of the vault key exists today is not something this repository can
verify, and Sahil is the only person who can answer it. Answer it before
filling in anything else in this file.

## Immutability, encryption, and the ransomware property

### The property that matters

> **A backup an attacker with your production credentials can delete is
> not a backup.**

Every other property of a backup — encryption, retention, frequency,
geographic redundancy — is subordinate to this one. Ransomware operators
do not encrypt your data and hope; they delete your backups first,
because they know that is what determines whether you pay.

**Verdict: this property DOES NOT HOLD for Ordence today.**

The reasoning, plainly:

- Neon's PITR history and branches live **inside the Neon project**.
  Whoever holds Neon account credentials can delete the project, and the
  history goes with it. `CONFIGURED` — PITR exists; `ASSUMED · UNTESTED` —
  no one has confirmed what deletion protections, if any, are enabled.
- The R2 bucket is reachable with the `S3_ACCESS_KEY_ID` /
  `S3_SECRET_ACCESS_KEY` that the running application holds. Unless
  object-lock or versioning is switched on, those credentials can delete
  objects. `ASSUMED · UNTESTED` — neither versioning nor object lock has
  been confirmed as enabled on the bucket.
- There is **no off-provider copy** on a schedule. The existing runbook
  says this too. Manual customer exports are not a backup regime; they
  are a feature that a customer may or may not use.

Saying so is not pessimism. A DR document that claimed otherwise would be
the expensive kind of wrong.

### What would make it hold

Three changes, in the order of how much they buy per hour of work:

1. **R2 object lock (compliance mode) + versioning on a dedicated backup
   bucket.** Under object lock, a delete issued with the application's
   own credentials does not remove the object; it writes a delete marker
   over a version that remains until the retention period expires. This
   is the single change that converts "a backup" into "a backup an
   attacker cannot destroy". `ASSUMED · UNTESTED`.
2. **A write-only credential for the backup bucket.** The job that
   uploads dumps needs `PutObject`. It does not need `DeleteObject`, and
   a token that cannot delete cannot be used to delete. Separate token,
   separate bucket, stored outside the application environment.
   `ASSUMED · UNTESTED`.
3. **A scheduled `pg_dump` to that bucket, encrypted with a key held
   off-platform** — `age` or `gpg` to a public key whose private half is
   not in Railway. This is the Level 4 answer: it is the only copy that
   survives losing the Neon account, and it is the only copy an attacker
   inside your infrastructure cannot decrypt. `ASSUMED · UNTESTED` — not
   built.

⚠️ **And each of those three creates a new restore path that is itself
untested.** An encrypted off-provider dump introduces a fourth thing that
can be missing on the day: the decryption key. Add the mechanism, then
add a row to the results table below, then run it. In that order.

### Neon retention

`CONFIGURED` — the project has a history retention window; PITR to any
moment inside it is continuous. `ASSUMED · UNTESTED` — the current value
is not recorded anywhere in this repository, which is why Step 1 above
makes you go and read it. Whatever it is, it is the hard ceiling on RPO
for every scenario except total account loss, where the ceiling is the
age of the newest off-provider copy — and today there is none.
