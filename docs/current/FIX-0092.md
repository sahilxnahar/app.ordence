## The cause. It was mine, and it was not the obvious one.

`0091` put `FORCE ROW LEVEL SECURITY` on `reserved_slugs` with

```sql
reserved_slugs_write  FOR ALL  WITH CHECK (app_platform_scope())
```

`app_platform_scope()` reads `current_setting('app.platform_scope')`, which is unset by default. So `0092`'s plain `INSERT` was refused:

```
ERROR:  new row violates row-level security policy for table "reserved_slugs"
```

That is statement 2. That is your screenshot.

⚠️ **`FORCE` is exactly why this was easy to miss.** Plain `ENABLE` does not apply to the table **owner**, and migrations run as the owner. `FORCE` exists so the owner is *not* exempt. Correct for the application, surprising for a migration, because every migration written before that table was forced worked without this line.

🔴 **And it is why my drill passed.** I applied `0092` locally as a **superuser**, and a superuser bypasses RLS entirely. **I tested it in the one configuration that could not fail.** That is the same mistake I have been naming in other people's work all week: I verified the file, not the situation.

**I have now reproduced your exact error** on PostgreSQL 16 as a non-superuser role without `BYPASSRLS`, applied the fix, and proved the fix is load-bearing by removing it again:

```
without SET LOCAL  ->  ERROR: new row violates row-level security policy for table "reserved_slugs"
                       ERROR: current transaction is aborted
with SET LOCAL     ->  INSERT 0 3
                       COMMIT
```

The fix is one line, inside the transaction, doing exactly what `withPlatformScope(reason, cb)` does in the application:

```sql
SET LOCAL app.platform_scope = 'on';
```

## ⭐ The new gate, built on what the evidence does support

`npm run check:sql-rls-writes` , walks `SQL-FILES/` in order, builds the set of tables that have had `FORCE ROW LEVEL SECURITY` enabled, and fails on any `INSERT`/`UPDATE`/`DELETE` against one of them in a file that never sets the platform scope.

It immediately found something I had shipped to you: **`VERIFY-0091-neon-safe.sql` inserts into `tenants`, which `0014` forces RLS on.** For a role without `BYPASSRLS`, every probe in its section 7 would have been refused by RLS rather than by the thing being tested, so the CONTROL row would have read *"the guard is refusing legal names"* and rows 2 to 5 would have reported **PASS for the wrong reason**. A verify file that passes for the wrong reason is worse than no verify file. Fixed with the PL/pgSQL equivalent, `set_config('app.platform_scope','on', true)`.

16 older files are grandfathered by name, each named individually so adding to that list is a visible decision. They are already applied, and an applied migration is corrected by a new numbered file, never edited in place.

🔴 **`0091` is on that list.** Its section 6 backfill of `tenant_slug_history` sits after `FORCE RLS` on the same table. It did not fail on your database, and section 3 of the new `0092` tells us why.
