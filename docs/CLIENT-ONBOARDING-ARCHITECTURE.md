## What you asked for, in one sentence each

1. **One-click client creation** — you fill one short form; everything else builds itself
2. **Guided setup for the client** — their first login is a wizard, not an empty dashboard
3. **Hide what they don't pay for** — the sidebar shows only what their plan includes
4. **Fewer, clearer screens** — grouped by what a person is doing, in plain English
5. **A subdomain each** — `acme.ordence.com`

## Part 1 — The one idea the whole design rests on

> **There is exactly ONE list of what Ordence can do, and everything reads
> from it. Nobody maintains a second copy.**

Today the truth is scattered: a hard-coded sidebar, a 53-key entitlement
catalog, a 500-row feature map document, and your own memory of which client
asked for what. Four copies drift. They always drift, and the drift is silent —
a client sees a menu item they didn't pay for, or doesn't see one they did.

The fix is a **module registry**: one file, one entry per module, carrying
everything anyone needs to know about it.

```ts
// lib/modules/registry.ts   ← the single source of truth
{
  key:        "contracting.ra_bills",   // matches the entitlement key exactly
  label:      "Contractor Bills",       // plain English, not "RA Bills"
  description:"Running-account bills, retention, TDS and EPF checks",
  group:      "site",                   // which sidebar section
  href:       "/contracting",
  icon:       HardHat,
  tier:       "professional",           // cheapest plan that includes it
  industries: ["real_estate","construction"],   // hidden for a law firm
  status:     "live",                   // live | beta | coming_soon
}
```

Then:

- **The sidebar** is generated by filtering this list through `evaluateFeature()`
- **Your admin console** renders this list as toggles
- **The setup wizard** offers the modules the client's plan includes
- **The feature register** is generated from it, so it can never be stale

One list. Four consumers. **Adding a module means adding one entry** — the
menu, the admin toggle and the register all update themselves.

This is also what makes "fewer, clearer screens" achievable rather than a
one-off tidy-up: `label` and `group` live here, so renaming "RA Bills" to
"Contractor Bills" is a one-line change that propagates everywhere.

## Part 2 — What happens when you create a client

Today: several manual steps across Clerk, Neon and Cloudflare.
After: **one form, six seconds, nothing manual.**

```
YOU FILL IN                        ORDENCE DOES
─────────────────────────────      ──────────────────────────────────────
Company name  "Acme Builders"  →   1. slug "acme", checked against
Subdomain     acme  [auto]            reserved words and existing tenants
Industry      Real Estate      →   2. Clerk Organization created
Plan          Professional     →   3. tenants row: slug, industry,
Admin email   ops@acme.com            branding defaults, settings
Modules       [✓ Land ✓ RA Bills →  4. subscription row on the chosen plan
               ✗ GST  ✗ Tally]      5. per-tenant entitlement overrides
                                      for anything off-plan you ticked
     [ Create workspace ]         6. roles seeded (owner/admin/member)
                                   7. admin invited by email via Resend
                                   8. audit entry: who created what, when
                                   9. → acme.ordence.com is live
```

**Every step in one database transaction.** A half-created tenant — Clerk org
exists, no `tenants` row — is the worst possible state: the user can sign in
and nothing works, and you cannot tell from either system what went wrong.
Clerk is the one external call, so it goes first and is rolled back explicitly
if the transaction fails.

**Two things this form deliberately does NOT ask.** Logo and colours — the
client chooses those in their own wizard, because they have the files and you
don't. And team members — the client invites their own people. Every field you
add here is a field you fill in for every client forever.

## Part 3 — What the client sees on first login

Not an empty dashboard with forty menu items. A five-step wizard, resumable,
skippable, with the last state remembered so a half-finished setup survives
closing the laptop.

```
┌─ Welcome to Ordence ──────────────────── Step 1 of 5 ──┐
│  ●━━━━○━━━━○━━━━○━━━━○                                  │
│                                                          │
│  1  Your company      name, GSTIN, address, fiscal year │
│  2  Make it yours     logo, banner, brand colour         │
│  3  Your team         invite by email, assign roles      │
│  4  Your first project                                   │
│  5  Done              here's what you can do             │
└──────────────────────────────────────────────────────────┘
```

**Step 2 is the one you asked about.** They upload a logo and a banner, pick a
colour, and see it applied live in a preview of their own sidebar. Files go to
the `DOCUMENTS` R2 bucket that already exists; the URLs go into the `branding`
column that already exists. The work is entirely in the UI layer.

**Where branding actually renders** — and this is the whole visible payoff:

| Surface | What changes |
|---|---|
| Sidebar header | Their logo instead of "Ordence" |
| Dashboard top | Their banner |
| Browser tab | Their favicon |
| Buttons, links, highlights | Their primary colour, via a CSS variable set on `<body>` |
| PDFs — invoices, demand notices, statements | Their logo in the header |
| Emails from Resend | Their logo and colour |

One CSS custom property set once in the layout drives the entire colour side.
No component needs to know about branding at all.

> ⚠️ **Colours get validated and clamped.** A client who picks pale yellow as
> their primary colour makes their own white text unreadable, then reports it
> as a bug in Ordence. Contrast against the button foreground is checked at
> save time and the nearest acceptable shade is offered.

## Part 4 — Your admin console

Three screens on `admin.ordence.com`. That host already exists and is already
separated in middleware — a tenant host physically cannot serve `/platform`,
and `admin.` serves nothing else.

**`/platform/tenants`** — every client, one row each: name, subdomain, plan,
users, storage, last activity, status. Search and filter. This is your morning
screen.

**`/platform/tenants/[id]`** — one client. Four tabs:

- *Overview* — who they are, when they joined, what they've used
- *Modules* — ⭐ **the screen you asked for.** Every module from the registry,
  as a toggle. Three states, and the distinction matters:
  - **Included in plan** — on, greyed, explained by the plan
  - **Granted as an override** — on, with an expiry date, and a note saying why
  - **Off** — available on a higher tier, with the upgrade named
- *Users* — their people, roles, last seen; suspend or remove
- *Danger* — suspend the workspace, export everything, delete

**`/platform/plans`** — what each tier includes, edited as a grid of ticks.
Changing a tier changes every client on it at once, so this screen tells you
how many that is *before* you save.

> ⚠️ **Every toggle writes an audit row** — who flipped what, for whom, when,
> and why. Not optional. When a client asks in nine months why they lost access
> to Tally, "I don't remember" is not an answer you want to give, and the
> `platform_tenant_flags` table already carries the shape for it.

## Part 5 — The subdomain, honestly

You chose a subdomain per client. It's the right product decision. Here is
exactly what stands between you and it — two items, both external to the code.

**1. Wildcard DNS — five minutes.** `admin.ordence.com` resolves today;
`test123.ordence.com` does not, which means no client subdomain would resolve
either. Cloudflare → ordence.com → DNS → Add record → `CNAME`, name `*`,
target `app.ordence.com`, **Proxied** (orange cloud). The wildcard *route* is
already declared in `wrangler.jsonc`; a route cannot match a hostname that
doesn't exist.

**2. Clerk production instance — half a day, mostly waiting for DNS.**

This is the real blocker and it is worth understanding precisely. Your Clerk
development instance serves its frontend from `pretty-shrew-42.clerk.accounts.dev`
and sets its session cookie on that domain. A user signing in at
`acme.ordence.com` would get a cookie belonging to a different domain
entirely — so they would be signed out the instant they arrived, forever, with
no error to explain it.

A **production** instance is different: its frontend lives at
`clerk.ordence.com` and its session cookie is scoped to `.ordence.com`, which
every subdomain shares. Sign in once, signed in everywhere under your zone. No
satellite-domain configuration needed — satellites are for genuinely different
domains, which is the later custom-domain feature (`crm.acme.com`), not this.

**So: the subdomain work is real but small. The Clerk production move is the
gate, and you need it before your first paying customer regardless** — the
development instance caps you at 100 users and stamps "Development mode" on
your sign-up page.

**Nothing else waits on it.** The registry, the sidebar, the wizard, the
branding and the admin console can all be built and used on `app.ordence.com`
this week. When Clerk production and the wildcard record are done, subdomains
switch on as configuration — the resolver is already written and tested.

## Part 6 — Fewer, clearer screens

Today: ~40 routes grouped by database table, named in accounting language.
Proposed: six groups named after what somebody is trying to do.

| Group | Contains | Replaces |
|---|---|---|
| **Home** | Dashboard, Search, What's new | dashboard, search |
| **Customers** | Contacts, Companies, Deals, Bookings, Leads, Partners | contacts, companies, sales/* |
| **Projects & Land** | Projects, Units, Land & Title, Approvals | land, sales/inventory |
| **Site** | Contractor Bills, Labour, Stock, Purchase Orders | contracting, labour, inventory, orders, purchases |
| **Money** | Invoices, Payments Due, Statements, Accounts, Taxes | receivables, statements, accounting, gst, gstr2b, tds, tally |
| **Setup** | Company, Team, Branding, Billing, Custom Objects, Automations | settings/*, objects, automations |

Two rules that make this stick:

- **A group with no visible modules disappears entirely.** A law firm sees no
  "Projects & Land". Not greyed — absent. Greyed-out menus are a permanent
  advertisement for what someone didn't buy.
- **Every name is what a person would say out loud.** "Contractor Bills", not
  "RA Bills". "Payments Due", not "Receivables". "Taxes", not "GSTR-2B
  Reconciliation" — that becomes a tab inside Taxes.

The database names, table names and API routes do **not** change. This is
label and grouping only, and it all lives in the registry from Part 1.

## Part 7 — Build order

Each section ships on its own and is useful before the next one starts.

| § | What | Depends on | Ships |
|---|---|---|---|
| **A** | **Module registry** — one file, 53 entries, plain-English labels and groups | nothing | The single source of truth. Nothing visible yet |
| **B** | **Entitlement-driven sidebar** — generated from A, filtered by plan | A | Clients stop seeing modules they don't have. The regrouping and renaming land here too |
| **C** | **Admin console** — tenant list, tenant detail, module toggles, audit | A | You can control every client from one screen |
| **D** | **One-click provisioning** — the form from Part 2, one transaction | A, C | You create a client in six seconds |
| **E** | **Client setup wizard** — five steps, resumable | D | New clients land somewhere useful |
| **F** | **Branding rendering** — logo, banner, colour, favicon, PDFs, email | E | Their workspace looks like theirs |
| **G** | **Subdomains switched on** | wildcard DNS + Clerk production | `acme.ordence.com` |

**A and B together are the biggest single improvement** and depend on nothing
external. C and D are what you personally touch every day. G is gated on the
Clerk move, which is on the critical path for your first customer anyway.
